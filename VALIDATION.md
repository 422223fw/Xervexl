# Validation — Xervexl 0.3, 13 October 2026

- **52 regression and integration tests passed**. New coverage checks exact rank 1 / 0 XP / 0 skill / 100 crowns starting values, logout/session invalidation, purchased quick-slots, account persistence, no-cost directional guard, wrong-direction protection, full-stamina counter disarm, attack cancellation, movement/body direction, deterministic world generation, independent filler bots per world, room isolation for melee/projectiles/drops, two consecutive arrow reflections, footing economics/probabilities and real rope pulling.
- Native C++20 build succeeded. The installed `build/Xervexl.exe` was replaced only after its old processes exited and its SHA-256 was verified against the tested candidate. The local authoritative server restarted at **0.3.0**, exposing **five worlds and 46 catalog items**. A final interactive launch verified a live window titled **Xervexl | motlon** after correcting Unicode window-message handling.
- Existing account JSON was privately backed up before activation. An automated comparison confirmed every existing account field, credential hash and progress value was preserved; only missing inventory/footing fields were added. No Active-Connection data was edited.
- Two simultaneous **installed** clients in **Oak Ruins** each reported **2 humans + 8 bots = 10 fighters**, 46 catalog items and no error. One used OpenGL; the other changed **Vulkan → OpenGL → Vulkan** within its existing session. Their short runs rendered 110 and 90 frames in about four seconds respectively, including renderer recreation on the switching client. These are smoke measurements with two concurrent processes, not performance or capacity guarantees.
- Actual GPU captures were visually inspected for first-person knife view in Winter Keep, bounded overhead view in Ember Basin, the five-world selector and inventory. A native sign-in/inventory/logout flow was exercised through window messages against an isolated synthetic account: the home screen showed **HELLO, UITestFighter** and **LOGOUT**, the owned knife appeared in inventory, and Logout restored **SIGN IN**.
- A deterministic 30-second bot simulation produced **133 attacks and 16 eliminations** after updating its forecast for free blocking. This checks continuing combat activity, not optimal AI or balanced human difficulty.
- Packaging uses a new staging directory and includes `arena_features.py`. Runtime accounts, credentials, backups, logs, screenshots and test data remain outside Git and the portable archive.
- Public hosting, SMTP delivery, long-duration operation, large populations and human balance/playtesting remain untested. Falling and ropes use simplified animation/constraints, and the rendering/collision limits in README.md still apply.

The last short run rendered 203 OpenGL frames in 4.01 seconds and 235 Vulkan frames in 4.01 seconds. These approximate 51/59 fps measurements are not load or performance guarantees.

- Public internet hosting, email delivery, long-duration operation, large population capacity and human balancing/playtesting remain untested. Graphics and collision still have the prototype limitations documented in README.md.

## Historical 0.1 checks

- Native C++20 executable built successfully using the installed portable WinLibs GCC 16.2.0 toolchain. Windows system APIs and the installed Vulkan loader are the runtime dependencies; no MinGW runtime DLL needs to be installed.
- **13 regression/integration tests passed**, including real HTTP requests from two independent sessions, shared movement, bot replacement, hashed/persistent accounts, equipment economics, authority, timed parry, damage, respawn, stale input and one-use password reset.
- A deterministic **30-second bot simulation** produced **164 attacks and 16 eliminations**. This checks that receding-horizon planning does not endlessly postpone attacks. It does not measure difficulty against human players or prove optimal play.
- Real native OpenGL and Vulkan clients ran at the same time and joined the same local server. The OpenGL capture reported **2 humans, 8 bots, 10 total fighters**. The Vulkan client still had 10 total fighters after the other client's departure, with filler bots returning.
- The last simultaneous run rendered **192 OpenGL frames in 4.00 seconds** and **228 Vulkan frames in 4.00 seconds** (approximately 48 and 57 fps). These are short smoke measurements on this computer, not benchmark or scalability guarantees.
- Home, arena and armoury frames were read from the respective GPU render targets and visually inspected. OpenGL and Vulkan both created real GPU-backed renderers; Vulkan loaded the assembled SPIR-V graphics pipeline successfully. Desktop capture was unavailable under Windows' existing time-limit screen; no parental/time-limit settings were changed.
- Public internet deployment, router/firewall reachability, SMTP email delivery, long-duration operation and large-player load have **not** been tested. They require a host and mail service, which have not been supplied.
- The runtime account JSON, tokens, logs, build tools and local screenshots are excluded from source control and the portable package.
